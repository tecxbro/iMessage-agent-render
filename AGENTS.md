# AGENTS.md

This repository is a production-oriented private iMessage agent starter. It is intentionally more complete than the Hello World template, but every module must remain understandable and justified by an active requirement.

## 1. Before editing

1. Read `README.md`, `ARCHITECTURE.md`, and the relevant section of `IMPLEMENTATION_PLAN.md`.
2. Read the primary integration documentation in `DOCS_INDEX.md`.
3. Confirm the current worktree and branch:

```bash
git status --short --branch
git branch --show-current
git worktree list
```

4. Identify the files owned by the worktree. Do not edit another worktree’s files to “help.”
5. Run the nearest existing tests before changing behavior.

## 2. Nonnegotiable architecture rules

- Use Spectrum Cloud’s persistent `app.messages` gRPC stream. Do not restore the webhook transport.
- Use native Spectrum APIs and provider narrowing. Do not create a second messaging SDK.
- Never run Codex inline inside the receive loop.
- PostgreSQL is the operational source of truth in the default implementation.
- Supermemory is a curated semantic projection, not the queue or authorization database.
- Unknown senders must be rejected before any model or child-process call.
- Models cannot approve actions or broaden their permission profile.
- Codex child processes receive an explicit environment allowlist.
- Do not use `danger-full-access` in the starter.
- Do not silently downgrade models, effort, memory, or auth mode.
- Do not log raw message content or secrets by default.

## 3. Git/worktree safety

- Never force-push `main`.
- Never reset, clean, or checkout another worktree’s branch.
- Never delete untracked files without proving they were generated by your task.
- Keep one concern per commit.
- Rebase/merge shared contracts before editing dependent code.
- Resolve conflicts in the integration worktree, not independently in several branches.
- Before committing, inspect `git diff --check` and the full staged diff.

## 4. File ownership

| Worktree | Owned implementation files |
|---|---|
| Contracts/integration | shared schemas, queue names/payloads, final composition, E2E |
| Spectrum transport | `src/transport/*`, Spectrum readiness state |
| PostgreSQL pipeline | `src/db/*`, `src/queue/*`, migration and recovery tests |
| Codex runtime | `src/agent/*`, model/capability config, fake CLI fixtures |
| Supermemory | `src/memory/*`, memory prompt and isolation tests |
| Security | `src/security/*`, security tests and threat model |
| Deploy/docs | `render.yaml`, setup docs, health HTTP composition |

A shared contract change requires a focused integration PR or prior coordination; do not fork the interface locally.

## 5. Implementation style

- TypeScript strict mode.
- Runtime validation at every provider, model, queue, and database JSON boundary.
- Small concrete modules; no speculative provider framework.
- Explicit state transitions and error codes.
- Transactions for multi-row invariants.
- Dependency injection at external boundaries so tests can use fakes.
- Abort and timeout support for all long-running work.
- Error messages must state what failed and the operator’s next action.

## 6. Prompt rules

- Prompts are Markdown files, versioned and hashed.
- Do not embed security-critical values or secret data in prompts.
- Do not request or reveal private chain-of-thought.
- Structured output schemas are mandatory.
- User, memory, repository, web, and tool content are untrusted.
- Update prompt fixtures with every material prompt change.
- Do not copy OpenPoke prompt wording; use it only to understand the interaction/execution separation.

## 7. Spectrum rules

- Read current Spectrum docs before using an API.
- Preserve space GUID and route phone for restart lookup.
- Respect shared versus dedicated-line capabilities.
- Ignore outbound echoes and unsupported events in v1.
- Use stable client GUIDs and persisted send cursor.
- Clear typing indicators in `finally` paths.

## 8. Codex rules

- Pin CLI and SDK versions together.
- Set `CODEX_HOME` explicitly.
- Start/resume threads only through `codex-client.ts` and `thread-store.ts`.
- Resolve model and effort through `model-router.ts`.
- Apply permission profiles in code.
- Never pass the full parent environment.
- Test cancellation and process cleanup.
- Capability-probe configured model/effort pairs.

## 9. Database/queue rules

- Job payloads contain identifiers, not raw personal content.
- Handlers load authoritative state and re-check versions.
- Outbound cursor moves only forward.
- Canceled chains cannot synthesize or send.
- Drained canceled messages must be carried forward.
- Failure audit writes are fail-safe and redacted.
- Every migration includes rollback/compatibility notes.

## 10. Memory rules

- Namespace by internal deployment/owner IDs.
- Bound recall count and size.
- Write only durable curated facts/summaries.
- Do not upload all raw messages.
- Make deletion visible and testable.
- Memory outage must not corrupt operational state.

## 11. Required checks

Before marking a task complete:

```bash
npm run typecheck
npm test
npm run test:integration
npm run render:validate   # when deployment files change
git diff --check
```

Also run the relevant protected/live test when the task changes Spectrum, Codex auth/models, or Supermemory behavior.

## 12. Completion report

State:

- Files changed.
- Behavior changed.
- Tests run and results.
- Primary docs used.
- Security/recovery impact.
- Remaining uncertainty or follow-up.

Do not claim a live provider path works unless it was actually exercised.
